# Промпт 1 — Перевірка spec на прогалини

**Задача для AI:** Перевірити мою специфікацію на прогалини та поставити уточнювальні питання.

**Промпт:**

> Я пишу концептуальну ER-модель для B2B CRM-системи. Ось моя специфікація (spec.md). Перевір її на прогалини, суперечності та постав уточнювальні питання. Не генеруй сутності чи атрибути — лише аналізуй те, що я написав.
>
> ```markdown
> # Специфікація моделі даних — B2B CRM
> 
> ## Намір
> Спроєктувати концептуальну ER-модель для B2B CRM-системи, яка фіксує роботу менеджерів із корпоративними клієнтами через угоди та товари. Модель має відображати бізнес-логіку, а не фізичну схему БД.
> 
> ## Сутності та атрибути
> - **Manager** (Менеджер): manager_id: UUIDv7 (PK), email: string (UK), full_name: string, created_at: timestamp
> - **Client** (Клієнт): client_id: UUIDv7 (PK), company_name: string, contact_email: string (UK), created_at: timestamp
> - **Deal** (Угода): deal_id: UUIDv7 (PK), client_id: UUIDv7 (FK → Client), manager_id: UUIDv7 (FK → Manager), title: string, amount: float, status: string, created_at: timestamp
> - **Product** (Товар): product_id: UUIDv7 (PK), name: string (UK), price: float, description: string (optional)
> 
> ## Зв'язки
> 1. Manager → Deal (1 : 0..N): Один менеджер веде від 0 до багатьох угод; кожна угода належить рівно одному менеджеру.
> 2. Client → Deal (1 : 0..N): Один клієнт має від 0 до багатьох угод; кожна угода стосується рівно одного клієнта.
> 3. Deal ↔ Product (M : N): Одна угода включає щонайменше один товар (1..N); один товар може входити в 0 або багато угод (0..M).
> 
> ## Критерії прийняття
> 1. Артефакти: model/er-diagram.mmd, model/er-diagram.png.
> 2. Концептуальна модель: бізнес-сутності та доменні зв'язки, не фізичні таблиці.
> 3. Нормалізація (3NF): залежність лише від PK, без транзитивних залежностей.
> ```

**Відповідь AI:**

Аналіз вашої специфікації виявив кілька моментів, які варто уточнити:

1. **Статус угоди (`status` у `Deal`):** Чи має поле `status` фіксований перелік бізнес-значень (наприклад: `new`, `negotiation`, `won`, `lost`), чи це довільний текст?
2. **Атрибути зв'язку Deal–Product:** Чи потрібна фіксація кількості одиниць товару (`quantity`) та індивідуальної ціни продажу (`unit_price`) в рамках угоди? Якщо так, чи планується асоціативна сутність (позиція угоди)?
3. **Обмеження на ціну та суму:** Чи дозволені від'ємні значення для `amount` або `price`? Чи сума угоди (`amount`) має обчислюватися як сума вартості товарів, чи це незалежне поле?
4. **Унікальність ідентифікаторів та типи даних:** Ви вказали тип `UUIDv7`. Чи вимагається уніфікація типів для всіх первинних і зовнішніх ключів у діаграмі?

**Мої відповіді на уточнювальні питання:**

1. На концептуальному рівні статус залишається типом `string` (допустимі бізнес-значення контролюються на рівні додатку).
2. На даному етапі концептуальна модель фіксує лише сам зв'язок між угодою та товарами без додаткових атрибутів (тому зв'язок є прямим M:N без асоціативної сутності).
3. `amount` — це доменне поле загального бюджету угоди, на концептуальному рівні математичні валідації не специфікуються.
4. Так, усі PK і FK без винятку мають бути типу `UUIDv7`, це буде зафіксовано як явний критерій.
