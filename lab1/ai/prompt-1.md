# Промпт 1 — Перевірка spec на прогалини

**Задача для AI:** Перевірити мою специфікацію на прогалини та поставити уточнювальні питання (без генерації сутностей).

**Промпт:**

> Я пишу концептуальну ER-модель для B2B CRM-системи. Ось моя специфікація (spec.md). Перевір її на прогалини, суперечності та постав уточнювальні питання. Не генеруй сутності чи атрибути — лише аналізуй те, що я написав.
>
> ```markdown
> # Специфікація ER-моделі — B2B CRM
>
> ## Намір
> Спроєктувати концептуальну ER-модель для B2B CRM-системи, що фіксує роботу менеджерів із корпоративними клієнтами через угоди та каталог товарів. Модель відображає бізнес-логіку, а не фізичну схему БД.
>
> ## Сутності та атрибути
> - Manager: manager_id, email (унікальний), full_name, created_at. Унікальний за email.
> - Client: client_id, company_name, contact_email (унікальний), created_at. Унікальний за contact_email.
> - Deal: deal_id, client_id (посилання на Client), manager_id (посилання на Manager), title, amount, status, created_at. Унікальний за deal_id.
> - Product: product_id, name (унікальний), price, description (необов'язковий). Унікальний за name.
>
> ## Зв'язки
> 1. Manager → Deal (1 : 0..N)
> 2. Client → Deal (1 : 0..N)
> 3. Deal ↔ Product (M : N): одна угода включає щонайменше один товар (1..N); один товар може входити в нуль або багато угод (0..M). Зв'язок прямий, без сполучної сутності.
>
> ## Критерії прийняття
> 1. Артефакти: Mermaid erDiagram у model/er-diagram.mmd; візуальний рендер у model/er-diagram.png.
> 2. Концептуальна модель: бізнес-сутності та доменні зв'язки, не фізичні таблиці БД.
> 3. Зв'язки M:N моделюються як прямий зв'язок між сутностями без сполучних сутностей, якщо зв'язок не несе власних атрибутів.
> 4. Нормалізація (3NF).
> 5. Узгодженість найменувань.
> 6. Модель не містить атрибутів, не зазначених у специфікації.
> ```

**Відповідь AI:**

Аналіз вашої специфікації виявив кілька моментів, які варто уточнити:

1. **Статус угоди (`status` у `Deal`):** Чи має поле `status` фіксований перелік бізнес-значень, чи це довільний текст?
2. **Атрибути зв'язку Deal–Product:** Чи потрібна фіксація кількості одиниць товару (`quantity`) та індивідуальної ціни продажу (`unit_price`) в рамках угоди? Якщо так, чи планується асоціативна сутність (позиція угоди)?
3. **Обмеження на ціну та суму:** Чи дозволені від'ємні значення для `amount` або `price`? Чи сума угоди (`amount`) має обчислюватися як сума вартості товарів, чи це незалежне поле?
4. **Унікальність ідентифікаторів:** Ви зазначили унікальність за `email`/`contact_email`/`name`. Чи достатньо цього для ідентифікації сутності на концептуальному рівні?

**Мої відповіді на уточнювальні питання:**

1. На концептуальному рівні статус залишається типом тексту (допустимі бізнес-значення контролюються на рівні додатку).
2. На даному етапі концептуальна модель фіксує лише сам зв'язок між угодою та товарами без додаткових атрибутів (тому зв'язок є прямим M:N без асоціативної сутності).
3. `amount` — це доменне поле загального бюджету угоди; на концептуальному рівні математичні валідації не специфікуються.
4. Так, унікальність за зазначеними атрибутами є достатньою для ідентифікації сутності на концептуальному рівні.
