# Специфікація моделі даних — B2B CRM

## Намір

Спроєктувати концептуальну ER-модель для B2B CRM-системи, яка фіксує роботу менеджерів із корпоративними клієнтами через угоди та товари. Модель має відображати бізнес-логіку, а не фізичну схему БД.

## Сутності та атрибути

- **Manager** (Менеджер):
    - `manager_id`: UUIDv7 (PK)
    - `email`: string (UK)
    - `full_name`: string
    - `created_at`: timestamp

- **Client** (Клієнт):
    - `client_id`: UUIDv7 (PK)
    - `company_name`: string
    - `contact_email`: string (UK)
    - `created_at`: timestamp

- **Deal** (Угода):
    - `deal_id`: UUIDv7 (PK)
    - `client_id`: UUIDv7 (FK → Client)
    - `manager_id`: UUIDv7 (FK → Manager)
    - `title`: string
    - `amount`: float
    - `status`: string
    - `created_at`: timestamp

- **Product** (Товар):
    - `product_id`: UUIDv7 (PK)
    - `name`: string (UK)
    - `price`: float
    - `description`: string (optional)

## Зв'язки

1. **Manager → Deal (1 : 0..N):**
   - Один менеджер може вести від нуля до багатьох угод.
   - Кожна угода належить рівно одному менеджеру.

2. **Client → Deal (1 : 0..N):**
   - Один клієнт може мати від нуля до багатьох угод.
   - Кожна угода стосується рівно одного клієнта.

3. **Deal ↔ Product (M : N):**
   - Одна угода включає щонайменше один товар (1..N).
   - Один товар може входити в жодну або багато угод (0..M).

## Критерії прийняття

1. **Артефакти:**
   - Mermaid erDiagram у файлі `model/er-diagram.mmd`.
   - Візуальний рендер у файлі `model/er-diagram.png`.

2. **Концептуальна модель:**
   - Моделювати бізнес-сутності та доменні зв'язки, а не фізичні таблиці БД.

3. **Нормалізація (3NF):**
   - Жоден неключовий атрибут не залежить від іншого неключового атрибута.
   - Усі неключові атрибути залежать безпосередньо від первинного ключа.
